### P1

**WR-05 · P1 · Open redirect on the brand domain · IMP**
- *Where:* `app/api/bff/auth/login/route.ts` (GET, `next` parameter).
- *Reproduction:* `GET /api/bff/auth/login?stub=1&next=/%5Cevil.example/x` → `303 Location: http://evil.example/x`. Also `next=/%09/evil.example` → `http://evil.example/`.
- *Cause:* `startsWith("/") && !startsWith("//")` does not stop backslash or tab forms that the URL parser normalises to `//host`.
- *Effect:* stub mode is the default for **any** deployment without the staging variables, so a public or preview deploy would expose an open redirect usable for phishing under the NuovaSolution domain.
- *Expected:* resolve with `new URL(next, origin)`, require the same origin and an allow-listed path prefix; and WR-06.
- *Evidence:* L4, reproduced twice (`probe-output.txt` P05).

**WR-06 · P1 · Stub mode fails open in any deployment; "never production" is a comment · IMP**
- *Where:* `lib/contracts/mode.ts`, all `app/api/bff/**`.
- *Observed:* with no environment set, `POST /api/bff/auth/login` accepts any email and password and sets a session; `POST /api/bff/signup` returns **201 "created"**; `GET …/login?stub=1` mints a session with no credentials. `integrationMode()` accepts any `NUOVA_API_BASE` once the three variables are set; nothing checks the deployment environment or the target host.
- *Effect:* stub surfaces are labelled on the pages (good), but a deploy that forgets the variables exposes a fabricated account flow; a deploy that sets them with a production base would proxy to production.
- *Expected:* fail closed outside local and explicit test deployments (for example when `VERCEL_ENV=production`): stub endpoints return 404 and auth surfaces render "not available"; staging mode verifies the target against an explicit staging allow-list.
- *Evidence:* L4 (P04, P06, P07), L1.

**WR-07 · P1 · Q&A request is rejected by the intake contract · IMP**
- *Where:* `app/api/qa/route.ts`.
- *Reproduction (L6):* site instance on :3108 with a throwaway tenant secret, `QA_INTAKE_URL` pointed at `qa-mock.mjs`, which enforces `WEBSITE_QA_INGRESS_CONTRACT_v1`. `POST /api/qa {"question":…}`.

- *Evidence:* L6 (`qa-mock.log`).

**WR-08 · P1 · Q&A expects a synchronous answer; the contract is accept-then-poll · IMP (blocked on API D1–D4)**

**WR-12 · P1 (staging) · Refresh-token cookie survives logout · IMP**
- *Where:* `app/api/bff/auth/login/route.ts` sets `nuova_refresh` with `Path=/api/bff/auth` (7 days); `logout/route.ts` deletes it with `Path=/`.
- *Reproduction:* `POST /api/bff/auth/logout` → `set-cookie: nuova_refresh=; Path=/; Expires=1970` (P09). A deletion must match the cookie's path; this one does not.
- *Effect:* after logout the browser keeps a 7-day refresh token. No refresh endpoint exists, so the cookie is also never used, while export v2 requires refresh then retry once on 401.
- *Expected:* delete with the matching path; implement refresh or stop storing the token.
- *Evidence:* L4 (Set-Cookie attributes), L1.
