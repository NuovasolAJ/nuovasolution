**(b) Does the deployed code use a key?** No. `9943660` has 11 prerendered static pages, no API route, no
middleware, no server action, no `process.env` read. No commit in the whole history of `main` ever added or
removed a Supabase or key reference in code or configuration. 0 key-shaped strings in 972 KB of live HTML/JS.
The deployed code has **no path that can read a key at runtime**.

**(c) Is a key present in the current runtime configuration?** **UNKNOWN.** Environment variables of the
Vercel project are not readable from here. Code without a consumer does not prove that no value is stored.
No `NO_KEY` is claimed. Fingerprint result: `key_match_449d518b2279 = unknown`.

**(d) Historical deployments possibly affected.** Any deployment of Vercel project `nuovasolution` whose
environment held the exposed key. Git cannot bound this: the history shows CLI deploys from a working tree
(`6035974`: "commit and deploy … stuck in working tree"), and the unpushed rebuild branch could have been
CLI-deployed from the old machine. Only the Vercel deployment list decides.

**Consequence for the revocation of secret `default`:** revoking it cannot break the deployed website,
because the deployed code never reads a key (b). Whether a copy of the value sits in the Vercel environment
(c) is an exposure question, not a precondition for revocation; after revocation any stored copy is inert and
should be deleted. The decision belongs to API.
